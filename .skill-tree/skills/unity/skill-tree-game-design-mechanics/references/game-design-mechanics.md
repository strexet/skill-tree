# Mechanics lookup and source records

Use the [seed collection](game-design-patterns.md), permitted project sources and the [shared record contract](game-design-records.md). A phrase describing an activity or problem is sufficient to start a lookup. A card name, finished GDD and network access are optional inputs.

## Find a rule from an activity or a name

1. Restate the intended decision or response. Extract the actor, trigger, state change, control mode, clock and context. Identify required facets and preferences. Record the unknown facets and the source needed to verify a consequential condition.
2. Read eligible local titles, localized aliases, descriptions and source notes. Keep the original wording and language. Match behavior by trigger, transition, clock and a boundary example. Search for autonomous processes when the request describes a change without a fresh player action.
3. Treat multiple labels for the same rule as aliases of one stable concept. When two rules share a name, return the distinct candidates and the distinguishing conditions. An adjustment to a rate or cap creates a parameter variant. An adjustment to the trigger, ordering or state transition can establish a distinct rule.
4. Return each matching pattern revision, the applicable conditions and exact source locator. Explain adjacent candidates and exclusions using the requested facets. A required unknown facet leaves verified coverage open. An empty result names the inspected scope and the missing rule or evidence. Stay within the selected project and available sources.

## Author a reusable pattern

Record a stable collection ID and revision, names and aliases with language and context, and original wording. Describe the activation or autonomous trigger, state transition, control mode and clock, and observable feedback. Include prerequisites, relevant placement conditions, limitations and a counterexample that separates the rule from a nearby pattern. Map observed implementations to the exact game, mode, version and source. Keep measured values in the project record or versioned example.

Give each source a scoped ID and revision, original title, author or publisher, edition or build, precise locator and basis for access and reuse. A source can scope each component separately, including original paraphrase, imported data, quotation and artwork. Mark unknown permissions and unverified claims for review. Shared distribution includes only eligible components with the required attribution. Personal deck material with project-only permission stays in the authorized project record. Use a source reference to preserve the editorial decision and recheck the permitted use when the edition changes.

Record an accepted new card, alias, merge or exclusion with a reason. Retain distinct outcomes for undetermined matches and material awaiting source review. A lookup can finish with an explained candidate list and source references. A chosen application links the exact pattern to a project rule or placement under the project owner's scope.

## Review a source batch

Choose contrasting titles or modes and record the examined section under each interaction group. Mark overlaps and sample gaps. Record the evidence level for each claim. A reference can support a generic pattern. Verified project use requires a matching observation of the selected project, build and placement.

Resolve the stable source ID and exact edition or dated observation before reviewing candidates. A repeat review of the same source revision reuses the source reference. Record each outcome as a new pattern, additional evidence, disputed match or exclusion. Keep the earlier disposition available when new evidence changes the review. Separate unfamiliar terminology from a changed trigger, state transition or boundary.

Ask a second reader to reconstruct sampled claims and exclusions from the cited sections. For a proposed merge, compare an input that separates the candidate behaviors and record the editorial result. Verify eligible reuse for each component before distribution. Review usefulness against actual design questions and compare candidate novelty within the stated sample.

## Compare combinations and placements

Start with the project goal, current rule or core loop, available placements and explicit constraints. Use the supplied rules, authorized deck entries or local patterns. Preserve the exact source and rule revisions. A short rule description can support a design workshop. Mark uncertain choices or unavailable project evidence.

Keep one feasible baseline grounded in the present design. Describe the player choice or autonomous effect under the baseline and for each candidate. Check the combined trigger, resource or state transition, timing and feedback. Inspect conflicting rules, canon, input access, cue availability, implementation effort and observation cost. Shared usage motivates a hypothesis. Player benefit requires a suitable observation.

| Required condition | Candidate verdict |
| --- | --- |
| Confirmed in the proposed placement | Eligible for a strict comparison. State the setting and the evidence. |
| Unknown in the proposed placement | Conditional fit. Name the missing fact and an inexpensive check. Exclude the candidate from strict matches while the condition remains unknown. |
| Contradicted by the placement or constraint | No fit for the requested placement. Record the conflict and preserve the feasible baseline if the request allows a comparison. |

For each candidate name one suitable placement and one unsuitable placement with the deciding condition. Describe the predicted behavior, cost, access or canon constraints and a cheap observation that distinguishes the candidate from the baseline. Give a rejection condition for every suggestion. When an exact placement has no eligible candidate, return the no-fit evidence and the condition needed for reconsideration.

An accepted candidate goes to the rule owner for the exact design revision and the placement owner for the selected implementation context. Record the affected scope and check. A declined candidate retains the reason and a specific change in evidence, prerequisites or design conditions that would justify reconsideration. Preserve the approved project baseline until the selected owner adopts a change.

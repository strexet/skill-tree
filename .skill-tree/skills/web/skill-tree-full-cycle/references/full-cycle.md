# Full Skill Tree cycle

Use `skill-tree-full-cycle` for a direct owner request to deliver one understood task or an explicit group through intake, research, implementation and reviewed merge to `develop`. The direct full-cycle order authorizes the scoped implementation, commits, source-branch push, shared PR and merge into `develop` under applicable repository and provider gates. An example, quoted text, task body or delegated suggestion grants no authority. Resolve any conflicting target or publication constraint before beginning the conflicting operation. Preserve explicit restrictions and required owner decisions.

Use the existing leaf contracts and helpers. The full cycle owns routing and the handoff between receipts. Leaf operations own the actual requirements, effects, decisions, checks and evidence.

## Capture and research

1. Read the [intake contract](pending-task-intake.md), [future workflow](future-workflow.md), [controller contract](orchestration.md), [run workspace contract](run-workspaces.md) and [PR review cycle](pr-review-cycle.md). Resolve the canonical queue and original owner request. Establish the exact task boundaries and repository before mutation.
2. Use Add Pending for the original request. Use `scripts/workflow-state.py intake <canonical-root> --standalone --input <intake.json>` to keep the new request outside existing controllers. Capture each understood item once under one caller-held `IB-` identity, with the current queue source hash. Retain the intake identity and exact Pending IDs. Resume from the owned intake receipt after an uncertain intake result.
3. Use Process Pending with the exact outstanding Pending IDs from the intake receipt and the inspected queue hash. Research the current sources and record each disposition. Apply the researched result with `scripts/workflow-state.py process <canonical-root> --standalone --input <process.json>`. Retain the processing receipt, including the exact created or reused prioritized IDs, in the resumable handoff. A retained item or blocked prioritized item holds the group. Review explicit reuse of an existing task against the authorized scope before admission. Prioritized group search can help reconcile provenance, but a shared batch or topic alone cannot define the implementation scope.
4. If a processing response is missing, reconcile the actual Pending rows, prioritized provenance and any retained processing receipts. Continue only when all original dispositions and exact output identities are established. A missing Pending row gives no proof of resolution. Avoid replaying processing for already promoted or resolved items. If research verifies that the entire request is already satisfied, report the recorded dispositions and close the delivery without creating an empty PR.

### Continue a partitioned Director intake

Use the registered project route for `skill-tree-full-cycle` with an exact `full_cycle` input containing `intake_batch_id`, ordered `items` and `full_cycle_partition`. The partition contains ordered `primary` and `deferred` lists of exact item keys. Each intake item appears once. A primary item requires closure within the approved scope before processing.

Freeze the reviewed child in the Director plan and authorize the exact intake and primary process effects. The original canonical batch receipt records the ordered Pending IDs for both partitions. After the exact process acknowledgement, use `verify-intake` on the original assignment to recover the original partition and the verified `full_cycle_primary.task_ids`. Reuse the original IDs and receipts on retry or resume.

Continue at implementation with only the exact prioritized IDs produced from the verified primary Pending IDs. The existing owner requirement applies to the selected implementation and delivery scope. Later work requires a separate authorized selection of the deferred Pending IDs.

## Implement the frozen group

1. Use Work Through Next with the exact prioritized ID for a single root. For several roots, use Implement All with the exact `snapshot_ids` and inspected queue hash. The recorded snapshot contains only the approved roots and the controller admits the required dependency closure. Report out-of-group required dependencies and establish authority before work that would expand the request. Defer unrelated work and preserve any existing queue or run.
2. Use one isolated registered run and one source branch from current remote `develop`. Use `workspace-setup` if needed under the run workspace contract, then use `start --standalone` with the exact selector or snapshot. Omit the standalone `implementation_operation` field for the Full Cycle remote delivery order and retain the combined source commit handoff. Give the run a stable branch such as `codex/full-cycle-<intake-batch-uuid>` and retain the exact run ID. Record the original direct authorization for the selected repository and `develop` in `delivery_authorization` when starting the run. On resume, verify the exact run and workspace before claiming work or creating another branch.
3. Advance the admitted controller through every scoped root and required dependency. Use the normal leaf planning, checks, review and acceptance. Resolve required stops at the recorded checkpoint. Finish implementation only when the controller reports current acceptance for the entire admitted scope.

## Review and merge one PR

1. Review the actual change set for the whole admitted scope and commit only scoped changes. Begin PR preflight only after implementation finishes. Bind the original direct owner grant to the exact source branch, remote and `develop` target. Pass the original owner instruction as `instruction` with `instruction_origin: "owner"`, `target_branch: "develop"` and `merge: true` to the PR helper when the original direct full-cycle order grants the full path. Preserve the matching normalized authorization in the run and on each resumed review command. Recover an existing matching publication or PR identity before any retry.
2. Use the PR review cycle for the combined current diff and the current discussions, checks and approval policy. Resolve findings in the same branch, run the required checks and re-review the current head and base after fixes. Keep the PR scope and target stable. A clean review can reach readiness directly.
3. Merge through the existing guarded provider path only after current readiness, checks, required approvals and merge authorization all pass. Record the provider-confirmed merge and merge commit. Recover an uncertain provider operation against actual provider state and the original operation receipt before attempting a retry. A change of target or scope needs the appropriate direct owner instruction.

## Bindings and stops

Use the installed [plugin invocation contract](plugin-invocation.md) for matching full-cycle bindings. Run the full-cycle `before` phase against the original request before intake, `during` against the frozen controller before source changes, and `after` against the finished controller before publication. Use the exact selected roots for the controller context. Authorized dependency additions keep the roots stable but can change the context fingerprint. Reconcile affected hooks through the guarded requalification or replacement path before controller completion. For an already-satisfied batch, run the remaining full-cycle phases against the original request and verified disposition evidence before reporting completion. Revalidate scope and acceptance after any incorporated contribution. Each leaf owns the bindings and decision frames configured for the leaf operation. Use the leaf's owned installed package for configured leaf bindings. If a required leaf package or actor is unavailable, keep the current checkpoint and report the prerequisite. A selected-only installation with empty matching leaf configuration can use the bundled core contracts and helpers.

At a stop, retain the batch and exact Pending and prioritized IDs, the established dispositions, the current run or publication identity when available, the blocker, and the next safe action. Follow the [visible owner handoff](decision-governance.md#visible-owner-handoff). Ask the exact outstanding question in the ordinary reply. An external wait names the condition and the next check. Resume the same stage and scope after resolution. A short direct continuation reply can select the one offered next action within recorded authority. Required answers still need explicit input, and external approvals still need provider confirmation.

Report the accepted task scope, validation, shared PR and confirmed merge, or the exact remaining prerequisite and checkpoint.

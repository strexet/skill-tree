# Plugin Binding and Invocation Boundaries

## Definition layer

The binding foundation describes owned operation anchors, independent binding occurrences, typed input contexts and dispatch identities. The definition layer performs no plugin or native host execution, creates no workflow metadata and grants no task, installation or publication authority. Composition and actual invocation use separate implementation contracts.

The ordered registry binding array is the sole order authority. Each occurrence has an independent stable ID, plugin ID, operation, anchor, enabled state, optional declarative condition, extra instruction text and arbitrary JSON parameters. Repeated plugin IDs at one anchor remain separate occurrences and share one installed package. Move and removal actions select an exact occurrence ID; moving preserves identity and removal preserves every other occurrence.

## Trusted anchors and location resolution

`createAnchorCatalog(operations, {boundaries, named, aliases})` derives the actual owned operation set from the supplied operation catalog. A trusted boundary record contains the owned operation, a stable implementation version, accepted context kinds and an actual callable handler. Boundary handlers remain controller-owned executable registrations rather than plugin-supplied configuration. Catalog creation and location resolution never invoke a handler.

The returned catalog freezes boundary metadata, callable references and location mappings. The caller remains responsible for the actual host implementation and matching source/version identity; the catalog does not freeze function closure state. Location resolution rechecks actual callable records against catalog metadata and the catalog digest. JSON serialization supplies portable inspection data rather than a callable registration; a resumed host rebuilds the catalog from current owned dispatchers.

Every owned operation has before, during and after location definitions. A location remains unresolved when the trusted dispatcher catalog supplies no matching callable boundary. Named records map an operation and lowercase name to an existing trusted boundary ID. A name, source label or boolean executable flag supplies no callable boundary. The current source operation set can gain the management operation without changing a fixed operation count.

`resolveLocation(request, catalog)` accepts an exact operation/anchor object, a canonical location string or a declared free-text alias. Unknown or ambiguous mappings return an explicit unresolved status and reason. Free text cannot create an operation or executable boundary. The management agent can present a concrete verified mapping before configuration acceptance.

## Compilation and selection

`compileBindings(bindings, {packages, catalog, parameterDefaults, runOverrides})` validates occurrence identities, preserves array order and resolves locations. Effective parameters use upstream, project, occurrence and explicit run layers through the parameter resolver. Parameters remain separate from core context and authority. The compiled configuration digest covers ordered occurrences, effective values, conditions and the trusted catalog identity.

Compiled rows, effective values and ordering remain immutable. The compiled object retains the current callable catalog and a separate portable metadata projection. A JSON-roundtripped configuration requires recompilation against current owned dispatchers before selection; serialized resolved flags alone supply no executable boundary.

`validateContext(context)` checks typed request, project, document, snapshot, management, controller, Pending, task/group and review identities. Document paths remain repository-relative. Real Pending and task identities retain the required P/T forms. Context normalization supplies no fabricated task, queue or controller. Ordinary core selection, existence, admission, authorization and writer/installation guards remain mandatory outside definition validation.

Pending contexts carry Pending identities without premature task identities. Task/group contexts can retain real Pending provenance. Controller and review contexts can carry actual task identities when applicable. Request, project, document, snapshot and management contexts remain task-free; nonapplicable task identity fields reject validation.

`selectBindings(compiled, event, context)` selects enabled matching occurrences in configured order. Missing callable locations and incompatible context kinds remain visible unresolved entries rather than successful integrations. Declarative conditions support booleans, equality, membership, presence, all, any and negation over JSON-pointer context fields. Unknown executable condition forms reject validation without evaluation.

`moveBinding(bindings, id, index)` and `removeBinding(bindings, id)` return independent ordered copies. Missing IDs, duplicate IDs and invalid move positions reject mutation. Lifecycle proposals still own persistent configuration changes, exact confirmation and frozen parked-run reconciliation.

## Delivery and lineage identities

`dispatchIdentity(binding, event, context, inputs)` separates a stable delivery key from the current input digest. The delivery key binds occurrence ID, operation/anchor event and an explicit attempt identity when supplied. The input digest binds configuration, accepted context and effective parameter data. Controller and leaf bindings remain separate deliberate calls.

Selection returns the actual trusted boundary ID in the event. A named occurrence mapped to the same boundary uses the selected event without losing the occurrence identity. A mismatched event or a forged boundary hint cannot redirect an occurrence into another anchor.

The configured binding anchor remains separate audit data from the actual event anchor. Renaming a mapping to the same actual boundary retains the delivery key for the same occurrence/event while the changed configuration and binding data change the input digest.

`classifyDelivery(identity, previous)` distinguishes a new or distinct delivery from exact replay. A matching delivery key with changed inputs rejects conflicting replay. The definition helper records no invocation receipt and establishes no successful execution. The runtime reconciles original uncertain attempts and persists actual observed outcomes.

`enterLineage(lineage, identity)` rejects active re-entry of the same occurrence at the same boundary. Different occurrences of the same plugin remain valid, including a finite A-to-B-to-A chain. Sequential stage history and active recursive lineage remain distinct concepts. A changed configuration or source requires current verification and explicit parked-run reconciliation rather than silent replay.

## Standalone composition and boundary preparation

The composer reads verified owned plugin state as data and emits only the selected operation resource closures. `resolveInputs(root, operations)` binds the registry, package inventory and ordered definitions to the actual registered operation catalog. `composeOperation(source, profile, operation, ownedFiles)` produces the operation-local `references/plugin-bindings.json` manifest and selected `plugins/<id>/upstream/` and `plugins/<id>/overlay/` resources. Repeated occurrences share one package copy while retaining every configured occurrence and parameter layer in order.

Generated instructions retain locked core governance and reference the bounded local manifest. Raw upstream resource bytes remain separate from owned instructions. Binary data and original byte-order marks survive copying and content hashing. Composition, installation, list and dry-run never execute upstream helpers, acquire dependencies or invoke a skill.

The bundled `scripts/plugin-hooks.js` uses the declared local helper closure. `prepareBoundary(packageRoot, request)` rebuilds current callable registrations from the owned operation declarations and verifies the copied manifest and package resources before selection. The manifest binds the actual composed owned instruction/helper/reference bytes, including domain replacements. The CLI bootstrap verifies the owned inventory with built-in readers before loading local dispatcher modules; module calls verify the inventory before scope-helper execution. Direct module callers retain responsibility for the trusted module entry. Local inventory checks detect partial content drift and supply no cryptographic origin proof against rewriting an entire trust root. Serialized executable flags never create a dispatcher. A missing local helper supplies no source or sibling fallback. The boundary scope process selects a fresh nonexistent Python bytecode-cache prefix before owned imports and disables cache writes. Existing cache bytes remain unchanged; the guard reads the verified Python source rather than an older matching cache. The execution guarantee covers the bounded guard process rather than arbitrary provider or host processes.

Boundary preparation keeps actual operation scope. Process Pending before/during preparation verifies the real selected Pending identities before promotion. Implementation During requires the current task-bound draft plan in the plan-review phase before current plan acceptance and source edits. An accepted plan requires explicit core reopening before another During contribution. Applying a plan-changing result and retaining the corresponding readiness obligation belongs to the invocation runtime; core governance then invalidates affected acceptance and requires fresh plan review. Read-only preparation creates no successful invocation, task promotion, source edit or fabricated result hold.

A false occurrence condition excludes the occurrence before context obligations. Boundary preparation returns a no-op for an empty selected/unresolved occurrence set without creating a queue or optional-plugin hold. Core-only entry points read the empty manifest and continue without requiring optional plugin tools. Configured unavailable locations, missing native capabilities and unsupported invocation adapters retain explicit prerequisites. Composition alone never reports a plugin as executed.

Registry, revision, content, order and effective configuration changes participate in composition and profile freshness. Refresh follows the owned stopped writer/installation barrier and explicit re-admission. A live registry edit never rewrites a parked run's recorded effective configuration or historical results.

A selected operation associated with an owned installation requires the associated live registry. Association binds the actual execution project, exact current package destination and operation, profile and destination identities, complete verified resource inventory and raw manifest digest. Canonical queue sharing, a profile filename, an operation name or copied registry-present metadata supplies no association. A relevant invalid ownership claim remains a prerequisite. Independent standalone copies and unrelated valid profiles retain standalone behavior; empty, disabled and condition-excluded hook sets create no new optional hold.

The CLI and workflow transport retain the invoked lexical package root alongside the verified actual helper closure. Resolving a claimed owned destination through a symlink cannot silently turn the claimed installation into an independent copy, including when the relevant profile becomes unreadable. The invoked lexical root alone grants no ownership or execution authority.

## Guarded invocation chains

The owned `plugin-invocation.py` engine stores schema-1 `HC-<uuid>` chains in `.skill-tree/invocations/hc-<uuid>.json`. A chain freezes the actual event, typed context, ordered binding definitions, package resources, effective parameters, execution policy, mode, bounded owner authority, executor and execution source/profile snapshot. `HI-<uuid>` attempts retain the original isolated actor, sealed public input, creation and dispatch evidence, transport result and accepted core transition. Chain hashes and integer revisions guard existing mutations. Reusing a request identity with different start inputs rejects mutation.

The workflow bridge derives selected task, Pending, document and controller fingerprints from the actual execution checkout and canonical queue. Unrelated queue edits do not change selected-task identity. Request, project, management and other task-free contexts create no fabricated task, implementation run or Future document. A linked controller records the chain reference without widening admitted scope. Review attachment binds the chain to the current review context; live chain admission supplements ordinary PR checks and publication authorization.

Selection runs against the latest accepted context at each cursor. Independent occurrences retain configuration order, including repeated packages at one anchor. Disabled or condition-excluded occurrences retain explicit skipped stages. A finite A-to-B-to-A sequence uses separate binding IDs and isolated actor lifetimes. Active re-entry of the same occurrence at the same boundary rejects recursion. An accepted prefix retains the exact earlier stage inputs after a later contribution changes the current context.

The chain separates three facts: an actor returned a transport result, the core accepted or incorporated the contribution, and the owning operation satisfied final readiness. `passed`, `findings` and `questions` results wait for guarded acceptance before the cursor advances. A `passed` result with unchanged current context can retain a no-change receipt. Findings, questions and changed context require an actual ordinary core transition or a current scoped core decision. A no-op task revision cannot resolve findings or questions. Genuine content changes retain incorporation evidence; unchanged dismissal requires the current accepted core resolution decision. `failed`, `unavailable`, `cancelled` and unresolved original attempts retain an unsatisfied obligation.

Applicable global and current-occurrence prerequisites gate preparation, dispatch, returned-result qualification and contribution acceptance. Requirements belonging only to another occurrence remain visible and gate the corresponding occurrence without blocking otherwise valid current incorporation or invalidating accepted prefixes. An A-to-B-to-A chain retains the accepted B contribution when the later A occurrence remains unavailable. Completed-chain inspection and readiness retain applicable outstanding obligations without relabeling historical completion as current success.

Task incorporation verifies an existing clarification revision and exact selected-task before/after fingerprints. Implementation During also seals the actual draft plan digest and full plan fingerprint. Plan incorporation verifies the latest ordinary orchestration plan event, the original previous plan and the current revised unaccepted frontier; unrelated task revisions cannot accept changed plan output. Core decision resolution binds the original chain, attempt, result digest, mode, authority and current scope. Plugin output alone cannot mutate a task or supply the required approval. The next occurrence receives the incorporated context; final clarification confirmation follows the completed chain. An intermediate revision receipt explicitly supplies no final confirmation. Task completion, Processing and controller/PR readiness consult applicable current chain obligations alongside existing core gates.

## Host delivery and private parameters

The current adapter supports an explicitly declared Codex `source-backed-context` capability. The host creates an actual isolated context, loads the pinned instruction/resource closure, dispatches the exact owned delivery and records actual producer evidence. The adapter supplies no native `Skill` call. A source label, prepared prompt, actor identifier or stored attempt alone establishes no actual execution. Missing capabilities remain prerequisites.

The public attempt seals reference-level parameters, extra instructions, package identity, context, configuration, execution snapshot, mode, authority and allowed execution policy. Task attempts also seal the bounded check-declared project source fingerprints. Invocation, returned-result recording and contribution acceptance recheck the original source keys; changed source bytes require explicit retry rather than relabeling an old result. Later ordinary implementation changes retain planning history and require the current core checks and review. Directory declarations use the bounded deterministic source closure. Mutable queue, navigation, invocation, clarification, decision, machine-local, artifact, checkpoint, run and task-outcome metadata occupy the existing guarded workflow plane and remain excluded from the additional project-source snapshot. Authored history research and plans remain source inputs when declared. The separate workflow plane preserves ordinary task incorporation and original-attempt recording without granting plugins metadata-write authority. The owned Node runtime resolves permitted secret references only for private delivery. The private envelope includes actual resolved values and separate input, delivery and resolved-parameter digests. The Node binding dispatcher supplies the original occurrence/event/attempt identity. Public ledger data retains references and digests rather than resolved secret values.

`workflow-state.py` exposes trusted in-process `private_delivery_provider` and `private_delivery_sink` callbacks for the original `hook-invoke` dispatch. JSON payloads cannot register callbacks. The provider returns the exact owned Node delivery envelope; the sink receives the same private payload after the original invocation state commits. Both callbacks run outside the canonical writer lock. A sink failure leaves the original attempt for explicit reconciliation. CLI callers can supply an ephemeral per-attempt secret map; private delivery output remains private host transport rather than an ordinary receipt or shared artifact. Host result capture and sanitization remain host responsibilities; the adapter performs no universal secret detection or result redaction.

Preparation verifies the owned manifest and copied source bytes before local helper execution. Node preparation, private resolution, actor execution, research and owner waits occur outside the writer lock. The writer transaction rechecks current source/resource fingerprints, scope, policy and relevant core frontier before committing chain state. Private machine-local package/execution locators reside under `.skill-tree/local/hook-locations/`; portable chain records retain no machine-root paths.

Applicable prerequisite and frozen-watch admission precedes both default private delivery and trusted cached provider callbacks. The writer transaction rechecks admission before chain or locator changes. Ordinary business transitions cannot replace frozen configuration or watch baselines with current drift; original reconciliation and explicit supported recovery retain separate authority. A rejected operation preserves original attempts, accepted prefixes and private locator bytes.

## Resumption and readiness

Prepared, invoking and unknown attempts retain the original `HI-` identity. Timeout or uncertain transport cannot silently create another attempt. Actual host reconciliation records unknown, failed, unavailable or cancelled status without claiming success; an unknown original still requires resolution. Cancellation and revoked authority permit original-attempt cleanup without resurrecting removed scope or asserting a completed contribution.

Explicit resume records the resolved condition and a new epoch while preserving accepted prefixes and original attempts. A retry receives a new attempt after unresolved originals receive reconciliation and a supported returned or failed occurrence receives an explicit retry. Mode or authority changes require actual owner-origin evidence and applicable parent policy. Source/profile or current-context changes invalidate affected continuation; old returned output cannot be relabeled as current. Resume preserves frozen package identities, occurrence order and parameter configuration. A completed chain cannot absorb changed context, policy or execution source through resume.

Configuration replacement uses a new chain with `supersedes_chain_id`, exact predecessor hash/revision and a current scoped core configuration-adoption decision. The predecessor retains frozen configuration, history and the replacement reference. Readiness follows the explicit replacement lineage and rejects missing or cyclic replacements. An explicit empty replacement records a configuration decision rather than a successful plugin invocation.

Live admission requires a completed current chain, matching execution resources, current context and current parent policy. Recorded successful task outcomes can retain exact consumed-task fingerprints for readiness inspection; removed or cancelled scope cannot launch another invocation. Consumed Pending readiness uses exact promoted or resolved processing receipts from the original linked controller. Missing historical fingerprints retain an explicit prerequisite rather than reconstructing successful execution. An unresolved original attempt blocks owned installation changes even before Future initialization. Malformed invocation state requires explicit recovery. Installation never resolves an outstanding invocation by refreshing packages over active work.

Completed readiness uses a dedicated read-only proof with `proof_kind: completed-readiness`. The readiness proof verifies current owned resources, managed association, frozen configuration and applicable outstanding requirements. The readiness path preserves accepted planning history after ordinary plan acceptance and later implementation; the readiness path does not rerun a draft-only During entry guard or rehash completed attempt project sources. Ordinary business paths reject a completed-readiness proof.

The workflow prepares readiness outside writer scopes and keeps the exact selected chain set, chain/locator identities, admitted context and original watch in an operation-scoped in-memory cache. Writer admission and commit recheck the current scope and matching proof without starting Node. Missing preflight, matching-chain additions or identity drift require a new outside-writer preflight. Core task/controller and PR readiness callers retain exact selection and publication boundaries. Empty reference sets require no Node helper, queue creation or external-plugin hold; the cache creates no persistent readiness ledger.

Every business write retains current admission. After an authorized atomic business commit consumes the selected scope, the exact derived-navigation-only follow-up retains the original chain, locator and watch checks without reconstructing consumed Pending scope. The navigation exception grants no later business write or new readiness acceptance. Readiness can inspect an exact validated successful finished controller archive; ordinary runtime continuation still requires the live admitted controller.

## Workflow helper interface

The bundled workflow CLI uses `python3 scripts/workflow-state.py <hook-command> <repository> --input <payload.json>`. `hook-read` also accepts `--id HC-<uuid>`. The bridge preserves canonical queue routing and the actual execution checkout. Existing queue mutations require the inspected `expected_source_hash`; existing chain mutations require `chain_id`, `expected_chain_hash` and `expected_chain_revision`.

| Command | Guarded purpose |
| --- | --- |
| `hook-start` | Freeze a stable `request_id`, actual event/context, bounded authority/executor and composed configuration; an empty core-only configuration returns a no-op. |
| `hook-read` / `hook-next` | Inspect recorded state or the next current prerequisite/action without recording execution. |
| `hook-prepare` | Seal the next eligible occurrence for an actual isolated actor with host creation evidence. |
| `hook-invoke` | Bind the original `attempt_id` and `input_digest` to actual dispatch evidence and private delivery digests. |
| `hook-record` | Record the original actor's observed result and matching delivery identity; exact duplicate results retain the original receipt. |
| `hook-accept` | Advance only after no-change acceptance or a verified ordinary core incorporation/resolution receipt. |
| `hook-reconcile` | Retain actual host reconciliation for an unresolved original attempt, including cleanup after scope removal. |
| `hook-resume` | Recheck an explicitly resolved condition, current scope/policy and frozen configuration before a supported retry. |
| `hook-pending` | Inspect unresolved original attempts without creating workflow state. |

The Node CLI `node scripts/plugin-hooks.js --input <request.json>` also accepts `--input -` for private stdin transport. Default requests prepare a boundary; owned runtime requests select `freeze-chain`, `occurrence-plan`, `delivery-data` or read-only `readiness-plan`. Node preparation returns data and starts no host actor. The workflow bridge obtains current proofs from the owned Node implementation; caller-supplied JSON proofs cannot replace verification.

## Evidence boundary

Pure module fixtures establish deterministic definition, identity and context behavior. Copied module fixtures establish the declared module dependency closure without a source checkout or sibling skills. General/web/unity copied-operation qualification covers only the declared composition and boundary assertions. Invocation state/bridge fixtures establish only the recorded synthetic controls. Actual source-backed host invocation, runtime hold qualification and candidate efficacy require matching separate evidence. Source and fixture results supply no native, universal host or candidate-effectiveness qualification.

## Optional immutable invocation policy

A frozen package adaptation can carry an `invocation_policy` for a report-only, single-attempt source-backed context. The original public input and private delivery retain the same policy separately from effective JSON parameters and extra instruction text. Default parameter values use the supported `upstream` and `project` layers; the optional `schema` validates effective values. Binding or run overrides affect ordinary input without expanding the owned tool/action policy or context lifetime.

Successful normalized reports under a frozen report-only publication review policy keep the status tag consistent with reserved top-level obligations. A nonempty `findings` or `questions` value requires the corresponding outcome tag; contradictory mixed success payloads fail recording. Empty reserved values, annotations and arbitrary nested JSON retain ordinary result-data behavior. Rejection preserves the original attempt and supplies no pass or cleanup. The host retains the raw producer input and reconciles the original attempt using actual context-end evidence.

A fresh-context policy applies to every original attempt, including retries of one occurrence. Producer-origin `context_end_evidence` identifies the original actor/context, attempt, input digest and delivery digest. Successful acceptance requires the matching ended context; a result field claiming cleanup supplies no producer evidence. The host owns actual context lifecycle and observation. Fixtures validate recorded identities and state transitions without proving actual actor behavior or universal session containment.

The metadata-only `requirement-plan` prepares frozen configuration and a completed-readiness proof before business phase admission. The proof freezes publication requirements without invoking an actor or creating successful execution. Ordinary start, prepare, private delivery, recording and acceptance reject the completed-readiness proof as business authority. Current PR phase admission and explicit publication attachments remain additional core gates.

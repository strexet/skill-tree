# Skill-Tree: Clarify Tasks

Flavor: general. Read the [concrete project profile](references/project-profile.md).

Read repository-owner rules before action. Exact prioritized selection, required dependency scope, checkpoint integrity, truthful evidence, owner authorization and commit/publication boundaries remain mandatory. A profile, installed flavor or stored checkpoint grants no execution or continuation permission. Read [validation policy](references/validation-policy.md) and [installation profile](references/installation-profile.md).

Read repository rules, [workflow](references/future-workflow.md), [metadata](references/workflow-metadata.md) and the selected task/source evidence. Use scripts/workflow-state.py clarify-start with exact unique prioritized task_ids and the inspected expected_source_hash. The session holds only the selected tasks; clarification creates no implementation run or worktree. Research source-answerable facts, then use clarify-round to register decision prerequisites, task/semantic-field bindings and recommendations. Present the complete independent question frontier and wait for actual owner answers. Record actual answer evidence through clarify-answer; apply decisions through clarify-revise, preserving identity, provenance and validation metadata. Recheck clarity and the next frontier after revisions. Use clarify-confirm only after actual owner confirmation of the current exact task scope and semantic fingerprints. Every mutation requires the inspected queue hash; existing sessions also require session hash and revision. Use clarify-read before resuming; clarify-resume reconciles source drift within the frozen selection, while clarify-cancel records ended discussion without successful required interview evidence. Keep research and waits outside writer locks. Completion reports clarification acceptance and leaves implementation to a separate instruction.

Generated prose follows [document rules](references/document-rules.md). Source-backed interview execution and native external-skill invocation remain distinct evidence.

Use repository-discovered tools and concrete profile recipes. Platform-neutral checks establish only the recorded assertions; product/runtime claims require matching evidence.

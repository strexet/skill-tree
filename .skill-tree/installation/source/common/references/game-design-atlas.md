# Project mechanics atlas and change impact

Keep the atlas in the consuming project's existing design records. A project without an atlas can start at `design/mechanics-atlas.md`. Use the [shared records contract](game-design-records.md) for immutable pins and ownership. A shared pattern describes reusable behavior. A placement records the behavior in one project and context.

## Record a placement

Name the project-scoped placement ID and revision, exact rule and optional pattern pins, owner and source. Identify the mode, scene, input phase or passive system, trigger, effective setting, clock, exceptions and dependencies on canon, art, feedback or other rules. Evidence names the inspected build, source or report, region examined, observed behavior and check attempt where available.

| Design state | Required record |
| --- | --- |
| Proposed | Intended use, proposer, applicable condition and next decision. |
| Accepted | Exact rule and placement revision, owner decision and allowed exceptions. |
| Declined | Candidate, decision reason and conditions for reconsideration. |
| Retired | Prior placement pin, reason, affected checks and replacement when known. The shared pattern remains available. |
| Observed use with unknown intent | Exact runtime or source observation, examined conditions and the owner who can confirm intent. |

Independently record evidence coverage. A confirmed use names the exact source or observed activation under the selected conditions. A suspected use names supporting clues and the missing observation. Unexamined scope names the scene, mode or system still to inspect. A supported exclusion identifies the inspected scope and why the rule cannot operate there. An approved design can retain open runtime checks. Observed use can retain unknown design intent.

## Inventory before authoring

Begin with a defined project, revision, search area and question. Inspect accepted rules, the callers of each rule and relevant assets or settings. Follow scene initialization, input phases, effective overrides and passive or unattended processes as applicable. Compare the source condition with the actual context. A matching name or configuration field suggests a candidate. Evidence of activation or an effective binding supports a confirmed use in the examined scope.

Return confirmed and suspected uses, explicit exclusions, contradictory values and unexamined areas. Name the next observation and responsible owner for each material gap. A read-only request returns the inventory and preserves project files. An authorized atlas update records only the verified project placement and decision evidence.

## Trace an accepted revision change

1. Resolve the original and revised rule pins and name the changed facts. Preserve original placements and check receipts.
2. Compare known placement references, effective settings, conditions, dependencies and exceptions against the changed facts. Inspect affected runtime overrides and passive systems explicitly.
3. Mark known dependent placements and checks for review. Record uncertain links with evidence needed to resolve each link. Select an unaffected control with an explicit reason.
4. Check whether a cosmetic fact participates in a cue, timing, visibility or other dependency. A cosmetic edit without a relevant dependency preserves the behavioral check. Reopen only the affected presentation or behavior when a cue depends on the changed fact.
5. Resolve new coverage on the exact build or source. A retired placement keeps historical rationale and links. Shared catalog updates preserve project records and authority. Promote a local discovery to a shared pattern only after independent editorial review and acceptance of the eligible source material.

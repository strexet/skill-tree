# Installed Plugin Inventory and Removal Plan

## Scope and existing owners

Task T-10528edd-4542-4c26-b8b3-738ffc00d791 exposes the existing single installed registry and exact-ID removal. The lifecycle already owns pinned package records, dependency validation, ordered occurrence mutation, matching proposal confirmation, replay and installation barriers. The source and parameter facade remains independently importable. Catalog persistence, the optional installation stage and the management skill remain owned by later admitted tasks.

## Interfaces and views

A new lazy management module exposes inventory, human formatting, removal preparation/application, exact occurrence unbind and activation configuration through the plugins facade. Inventory reads the existing registry without acquisition, recovery, workflow helper execution or writer locks. The facade loads management dependencies only for a management call. Source and parameter calls keep the existing import boundary.

Installed packages retain source/revision/content identity, relative destinations, package dependencies, recorded adapter/capability status and every configured occurrence. Occurrence rows retain distinct IDs, one-based global and point positions, operation/anchor, enabled state, conditions, reference-level JSON parameters and extra instructions. Human grouping supports plugin or integration point; grouping never rewrites array order. Configured and independently verified location metadata remain distinguishable. Enabled configuration supplies no successful invocation or readiness conclusion.

Known definitions remain a separate input owner. The inventory can display explicitly supplied known metadata separately from installed packages; an absent catalog is reported as unavailable rather than fabricated recommendations. Listing never acquires a direct source or creates known state.

Readable registry ownership drift remains visible with structured diagnostics. Malformed or foreign installed state reports an unavailable inventory and an explicit issue without recovery or ownership adoption. Unknown IDs and namespaces reject exact-ID mutation; no fuzzy package matching occurs.

## Frozen requirements and mutations

The existing Node HC reader becomes a reusable read-only record reader without weakening installer checksum/schema checks. Inventory reports frozen package/occurrence requirements separately from current project defaults. Canonical queue location alone cannot associate another execution checkout with the selected installation; private execution locators or exact recorded run mapping establish association, and uncertain association remains explicit. Frozen snapshots, historical results and pending attempt states remain unchanged.

Removal preparation selects an exact plugin ID, reports affected destinations and every occurrence, and exposes dependency, ownership, pending-attempt and frozen-requirement consequences. The original lifecycle proposal remains the mutation authority. Matching confirmation delegates the original proposal to lifecycle application, preserving stale/replay checks and barriers. A failed or cancelled proposal leaves installed state unchanged. Package removal clears every live occurrence of the selected package and preserves original local sources, core files, shared dependencies and unrelated content.

Unbind selects one exact occurrence and prepares the remaining ordered array through configure. Disable or enable changes activation through the existing lifecycle operation. Forgetting a known definition remains a distinct unavailable action until the known-definition owner exists. The API never interprets package uninstall as unbind, disable or forgetting.

## CLI boundary

The source installer adds --list-plugins --target <project>, optional --json and --group-by plugin|point. Read-only routing precedes flavor/provider selection and optional installation work. The installed manager exposes the same list route independently of the caller working directory and source checkout. Invalid mixtures reject before writes. Full removal interaction and optional setup remain in the later installer and management-skill tasks; typed removal APIs already provide exact proposal/application behavior.

## Current source boundaries

`.skill-tree/templates/operations.json` directs agents through bundled contracts. `.skill-tree/common/scripts/workflow-state.py` persists supplied intake, processing, clarification and validation results. `.skill-tree/common/scripts/pr-review-state.py` treats CLI review operations as metadata. Metadata helpers supply no general host prompt-execution engine.

The clarification interface records selected task identities, researched facts, question/answer rounds, revisions and semantic confirmation. Actual source and semantic guards preserve interruption/resume and prevent silence from supplying owner answers. A reusable clarification protocol supplies no verified external Skill invocation or automatic plugin activation.

`.skill-tree/lib/composer.js` protects locked slots, resolves local resources and composes standalone packages. `.skill-tree/lib/installation.js` stages owned generations, checks receipt/profile freshness and preserves stopped workflow state. A source URL or entry file supplies no complete sibling/native-tool dependency closure. External packages require owned composition, exact revisions, complete resources and maintenance inventories.

The source/parameter foundation and `.skill-tree/lib/plugin-lifecycle.js` provide explicit acquisition, inspected proposals, owned registry/package transactions, request recovery and rollback. Controlled local HTTP/Git and installed-project fixtures establish the backend assertions. Standalone hook composition and guarded source-backed invocation retain the separate evidence and limits in the [invocation contract](../common/references/plugin-invocation.md). The public management skill and optional installer setup remain separate implementation tasks; the core installer exposes no external-plugin wizard.

`.skill-tree/bin/install.js` offers flavor selection and writes provider installations. Existing `--yes` behavior supplies no external-plugin consent. The [installation interaction contract](plugin-installation-contract.md) defines a separate optional-plugin stage after verified core installation and requires one exact project proposal before plugin writes. The core-only default and repeat preservation remain independent of plugin consent. Offline/no-write dry-run and installation without skill execution remain binding boundaries.

The execution design separates locked preparation, host invocation outside the lock and guarded result recording. Exact task semantics/source, plugin/dependency revision, profile and review head/base identities support stale-result rejection and idempotent recovery. External output cannot replace task selection, acceptance, permission, independent approval or merge gates.

## Owner decisions and comparison proposal

The [approved workflow decisions](plugin-workflow-decisions.md) define the suggested placement for an explicitly installed/enabled Ponytail pilot as an additional bounded pass after full review and before PR readiness, with configurable placement preserving the complete core review. Core-only installation creates no Ponytail binding. An enabled pass must complete for the current review identity; unavailability or failure retains a visible block. Explicit disabling records no execution success.

An enabled post-processing interview retains a visible stable-ID task under an implementation hold until actual answers, revisions, rechecks and current mode-specific acceptance under W1. Auto requires legitimate bounded delegated acceptance; Manual requires actual owner confirmation. Core-only projects receive no mandatory global interview. Project defaults and explicit temporary run overrides remain separate; frozen effective configuration protects parked runs. Additional mandatory stages or operation splits require actual owner agreement.

The [approved cohort](../history/research/plugin-comparison-proposal.md) compares four applications across eight fixtures and two fixed repetitions per arm in W1 Manual. Each candidate competes with a no-plugin baseline. Both review arms share the actual complete core report, and the processing baseline retains the existing clarification protocol. The owner approved the narrower two-arm cohort and a negative-calibration scoring adjustment. The earlier market proposal remains historical.

The [comparison result](plugin-recommendation-evidence.md) records actual source-backed invocation, independent scoring and unavailable results in temporary Codex projects. Two Ponytail clean-fixture pairs reached matched completion with equal outcomes. The core review blocked both planted-fixture candidate passes while the planted defect remained open. Processing and documentation observations exercised guarded mechanisms but did not establish paired recurring gains.

Installation confirmation covers exact displayed versions, hook locations, enabled state and readiness effects. Available catalog entries remain distinct from the installed project-local registry and guarded removal lifecycle. No displayed recommendation supplies consent, no installation executes a skill and no hosted marketplace requirement follows.

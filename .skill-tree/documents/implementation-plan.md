## Internal phases and decision governance

Both modes use research, plan, plan review, implementation, required checks, review, finding resolution, fixes and re-review. The phases initially remain inside existing operations. A clean review completes without inventing a finding or a fix. Standalone planning/report commands and new release/retrospective operations remain outside the initial operation set.

Auto is the approved default. The executor supplies the question, options, recommendation and researched facts. A separate resolver chooses an option with a recorded rationale. Significant decisions receive an independent critic; substantive disagreement receives an arbiter. Required actors use distinct recorded contexts. A missing required resolver/critic/arbiter capability records unavailable/prerequisite evidence, preserves the unresolved decision and any task hold, and produces one concrete owner request or waits for an explicit Manual switch. The executor cannot supply a fabricated independent role. Manual sends the same question and recommendation to the owner in chat and awaits an actual answer at the decision checkpoint. Routine authorized actions continue between checkpoints.

[W1 policy](plugin-workflow-decisions.md#approved-decision-w1-internal-phases-and-decision-modes) bounds delegated product/technical choices and final specification acceptance by agreed goals, scope and constraints. Decision records retain the real actor, authority, rationale and review evidence. Out-of-authority requests and repeated no-progress disputes/failures escalate one concrete owner question. Agent agreement cannot replace required checks or applicable independent approval. Existing owner authorizations remain valid.

Project defaults support explicit per-run overrides. Effective configuration freezes selected mode, delegation, bindings, revisions and required capabilities. An explicit mode switch records a guarded transition and preserves accumulated task/session/run state. Changing project defaults never silently changes a parked run. A mode switch supplies no missing answer, successful check or expanded authority. Switching reconciles or explicitly cancels live actors under the original attempt/configuration before using the new mode. Late replies remain historical or stale evidence and cannot answer a new-mode question. Historical answers and receipts remain available, while readiness requires current-mode, current-authority acceptance; delegated Auto acceptance alone cannot satisfy Manual owner confirmation.

## Post-processing task quality

A configured interview or task-editorial obligation creates the visible stable-ID T-task and implementation hold atomically. No transient Ready interval precedes the hold. Core-only task creation has no plugin interview/editorial hold. Standalone Process Pending retains the developer-choice handoff; an explicitly launched controller continues only within the recorded root/snapshot after required obligations complete.

The approved combined sequence is processing, `writing-for-agents` wording review, `grill-me` clarification, task revisions, affected wording recheck, current final acceptance and Ready publication. Disabled optional plugins contribute no invocation. The same T-task and Pending provenance survive every round. Auto uses actual bounded delegated decisions; Manual uses actual owner answers and final confirmation.

| Configured post-processing plugins | Completion path |
| --- | --- |
| Neither editor nor interview | Core researched-task readiness and existing handoff; no plugin hold or invented plugin execution. |
| Editor only | Wording review, guarded revisions, affected wording recheck and current mode-specific acceptance. Semantic questions use the shared core clarification mechanism; no external interview is reported. |
| Interview only | Interview, revisions, clarity recheck and current mode-specific acceptance; no editorial invocation. |
| Editor and interview | The combined editor, interview, revisions, affected editorial recheck and current acceptance sequence. |

`writing-for-agents` has two distinct catalog applications: post-processing task wording and agent-facing skill/document maintenance. Task wording review checks clear goals/expected behavior, scope, observable acceptance, concrete source references and necessary context. Editorial proposals preserve task identity, required constraints, dependencies and the Goal/Touch/Validation/Acceptance structure. The adapter applies task-document rules rather than converting tasks into skill packages.

Semantic edits reopen affected questions and final acceptance. Unrelated settled answers survive. Supported formatting-only edits preserve semantic acceptance. An editorial edit affecting meaning returns to the relevant clarification branch before final acceptance; repeated internal passes use current input fingerprints. Unresolved required findings, unavailable enabled obligations or cancellation retain a visible hold. Explicit disabling/configuration reconciliation records the changed obligation without claiming execution success.

The shared clarification controller owns rounds, answers, revisions and acceptance. The interview plugin is not restarted on every internal question. After rework, only affected editorial/clarification obligations repeat. Post-processing placement is approved; application-specific incremental benefit remains unqualified until comparison.

## Plugin packages, invocation and installed management

A plugin descriptor binds a stable ID, exact immutable revision, entry path, content/resource digests, dependencies, license/attribution evidence, allowed bindings and explicit host/flavor capabilities. Required sibling skills, references, scripts and native prerequisites form a closed inspected resource set. Project-local owned copies and repository-relative metadata support standalone operation without the source checkout. Discovery URLs and mutable branches supply no executable identity.

The lifecycle stages resources, verifies ownership/content and activates package, bindings and registry through an owned recoverable transaction with locks/backups. Activation, update, rollback and removal honor the existing canonical installation/writer barrier, inspect retained active runs and require a stopped cleanup/handoff boundary for affected execution. A changed generation preserves workflow progress and requires explicit profile/configuration re-admission before continuation. Installation, dry-run, listing and composition execute no skill helper. Unknown ownership, escaping paths, unresolved essential requirements and destination drift reject replacement/removal; force never adopts or deletes unowned changes.

The project-local `.skill-tree/installation/plugins.json` registry owns installed IDs/revisions, destinations, dependencies, digests and every binding/enabled state. Human and machine views derive from the registry. An exact-ID removal command previews packages/bindings, checks dependents and owned content, preserves shared resources/core packages/unrelated files and retains historical receipts. Parked requirements remain visible after removal.

The Codex-first adapter binds attempt, exact task/group or review identity, resource closure, source/profile, mode/authority and effective configuration. Actual host invocation and returned results remain distinct from prompt preparation. Receipts distinguish passed, findings, questions, failed, unavailable and cancelled outcomes; real actor/context evidence and exposed usage accompany the result. Original attempts survive interruption and uncertain transport. Duplicate delivery is idempotent; conflicting replay or stale source/configuration rejects mutation. Writer locks exclude research, invocation and owner waits.

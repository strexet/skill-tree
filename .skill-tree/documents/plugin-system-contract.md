# External Skill Plugin Contract

## Contract boundary

An external skill plugin is a pinned instruction/resource package integrated through a bounded adapter at a selected existing-operation hook. The plugin is neither an arbitrary subprocess nor a native host plugin bundle. The contract defines lifecycle, composition and invocation obligations; executable capability requires the corresponding implementation and qualification. Approved W1/W2 and [W3 management policy](plugin-management-contract.md) in the [implementation plan](implementation-plan.md) and [workflow decisions](plugin-workflow-decisions.md) govern internal scheduling, decision modes and mode-specific acceptance. Qualified core governance supports bounded Auto decisions, explicit Manual decisions and current mode-specific clarification acceptance. The existing frozen session mode remains binding. Actual core actor evidence covers the bounded scenarios recorded in `.skill-tree/history/validation/plugin-system/core-orchestration-qualification.json`; external plugin invocation retains separate qualification.

The plugin system preserves exact task selection, dependency closure, source/check evidence, standalone installation and owner authorization. A plugin cannot replace locked invariants, mark core checks passed, change owner decisions, authorize publication or satisfy independent approval. Core-only projects receive qualified core W1 phases and decision governance with no optional-plugin readiness obligation. Plugins cannot create an unrelated global stage or silently replace core behavior.

The current source exposes the [source/parameter foundation and owned lifecycle backend](plugin-management-contract.md#owned-lifecycle-backend). Controlled fixture qualification covers acquisition and package/registry transactions. Selected standalone composition, boundary preparation and guarded chain/attempt state use the [invocation contract](../common/references/plugin-invocation.md). The source-backed host bridge separates original dispatch, returned results and verified core incorporation from final readiness. Bounded actual source-backed observations reside in `.skill-tree/history/validation/plugin-system/invocation118-native/`; scripted fixture-owner input remains separate from real-human approval. The current read-only inventory and typed exact-ID management APIs derive from the installed registry. The dedicated management skill and optional initial installation stage retain separate task acceptance; backend installation, prepared state or composition alone establishes no successful skill invocation.

## Identity and resource closure

Each descriptor has a stable lowercase plugin ID, display name, source URL/path, exact immutable revision or content snapshot, entry path, content digests, attribution/license evidence, resources/dependencies and explicit adapter/capability status. Curated IDs and noncatalog repository/skill/raw-document/local sources share the same pipeline. Source-host labels such as Claude do not restrict import. Original content/metadata and owned wrappers or adaptation overlays remain separate. Mutable branches, discovery counts and catalog labels never identify installed executable content.

Dependency closure includes sibling skills such as the supplied `grill-me` wrapper and `grilling`, linked local references/scripts/assets, and required native tools/capabilities. Native tool requirements have explicit supported, missing or unqualified state. Packages retain upstream bytes and license provenance. A wrapper alone cannot claim the delegated skill or native tool is installed.

Owned plugin resources use project-local copies and repository-relative portable paths. Installation rejects escaping paths, symlinks, unresolved required source content and conflicting identities. Missing native tools or unqualified host translation remain visible capability prerequisites; known registration and inert package installation do not claim runnable support. Unknown or modified destination ownership never permits overwrite, adoption or deletion through `--force`. Native helper scripts remain inert during acquisition, static composition, verification and listing.

## Lifecycle and installed registry

The lifecycle owns `.skill-tree/installation/plugins.json` as the canonical installed-plugin registry. Registry generations bind plugin identities/revisions, resource digests, destinations, dependency references, configured operation/hook bindings and enabled state. Curated/custom known definitions and installed state remain separate; the curated catalog is not an admission allowlist. Management views derive from the registry rather than another authoritative plugin list.

The installation default is core only, including the `skill-tree-plugins` operation, with no new external plugin selected. Repeat core installation preserves existing plugins. Optional setup during installation and later management share the [management flow](plugin-management-contract.md). The installer asks before resolving a remote source and asks separately before activating the exact proposal. One project proposal displays exact versions, required dependencies, destinations, hook locations, enabled state and readiness effects. Actual install confirmation installs and enables precisely the displayed configuration. A changed proposal requires matching consent. Skip acquires/enables no new plugin and preserves existing installed state. Installation never executes a skill or starts a workflow.

Package generation, registry and bindings activate through one owned recoverable installation transaction with complete staging, ownership checks, locks and backups. Activation, updates, rollback and removal retain the canonical installation/writer barrier, inspection of retained active runs, stopped cleanup/handoff and explicit re-admission after a changed generation. Repeat installation can verify a matching generation. Updates, rollback and removal preserve task/run history and reject unknown or conflicting content. Dry-run, ordinary composition and installed listing remain offline and write-free.

Management distinguishes unbind, disable, uninstall and forget-known. Exact-ID removal previews the selected owned package and every live project binding referencing the package, then removes the package and all current bindings through the lifecycle and retains core packages, unrelated files and shared dependency resources. Remaining dependent plugins are explicit prerequisites rather than silently removed. Removing a required plugin leaves a visible missing requirement for a parked run; removal never reports successful invocation. Original local sources remain untouched; uninstall normally retains the known entry for reinstall.

## Hook map and configuration

Bindings have independent identities and identify any owned operation, a `before`, `during`, `after` or registered executable named anchor, deterministic order, optional conditions, enabled state and parameters. Hooks are bounded extension points inside the named operation. `during` contributes an additional scoped pass and preserves the complete core operation. The [built-in anchor map](implementation-plan.md#approved-integration-anchors) supplies standard boundaries; W3 extends placement across all operations and executable custom named anchors. Explicit controller/leaf bindings are distinct calls, while binding/event identity prevents accidental repeats and lineage exposes recursion/cycles. Plugin descriptors additionally constrain compatible phases, input identity and capabilities; operation support never implies every plugin supports every phase. Before/during Processing retains selected Pending identities; T-task clarification starts only after promotion.

An anchor contains an explicitly ordered sequence of binding occurrences. Every compatible catalog/custom plugin can appear more than once at the same anchor with independent IDs, parameters and conditions. Initial setup and later management can add, move or remove an exact occurrence; moving preserves identity and confirmation covers the exact resulting order. Composition preserves multiplicity. Dispatch runs sequentially against accepted guarded context, distinguishes finite A-to-B-to-A sequences from recursion and deduplicates only the same binding/event/attempt. Per-occurrence receipts support interrupted resume under frozen configuration; later expected edits preserve stage-input history without bypassing current final checks. The [management contract](plugin-management-contract.md#extensible-placement) defines the generic controls and example.

For an explicitly selected pilot, suggested placement is an additional Ponytail pass after the complete core review and before PR readiness, plus an enabled post-processing interview before implementation eligibility. Other approved placements remain configurable. Enabled review failure, unavailability or stale results block PR readiness. An enabled processing interview creates a visible stable-ID T-task under a hold; actual mode-specific answers, revisions, rechecks and current acceptance precede Ready publication. The configured task-editorial application adds wording review and affected recheck under the [post-processing completion paths](implementation-plan.md#post-processing-task-quality); an editor-only configuration uses shared core clarification without claiming external interview execution.

PR initialization freezes configured review obligations in the existing publication record. Metadata-only requirement preparation supplies no business execution proof. Phase-specific conditions and current explicitly attached accepted complete stages determine readiness; an enabled never-started pass, unrelated completed chain or skipped occurrence at another boundary supplies no successful pass. Current publication/core phase guards precede private delivery and metadata writes. A persistent disable requires accepted configuration reconciliation and retains the historical obligation. Guarded plugin findings join the ordinary publication finding ledger without replacing the complete core report; actual fixes, checks and re-review remain mandatory. Generic DG acknowledgement cannot complete returned review findings without the guarded publication ledger. After admission requires a resolved current core report. Evidence-backed dismissal with unchanged bound inputs preserves the accepted pass and source history; an internal report update supplies no automatic replay trigger. Registered aliases retain the current canonical boundary identity.

Project defaults support explicit temporary per-run overrides. Effective configuration records resolved bindings/order/conditions, plugin revisions, adapter/capability status, mode/authority, parameters and outcome policy. Parameter values resolve upstream defaults, project defaults, binding values and explicit run overrides. Extra instruction text and arbitrary JSON stay separate from core execution fields; optional schemas and value origins remain visible. Secret references remain redacted references in views/history. A configuration digest binds the complete effective snapshot to the run/invocation and remains frozen across resume. An explicit persistent edit does not silently replace an existing run configuration. An explicit disable/configuration change has a distinct recorded outcome and never counts as a successful pass or completed interview. Explicit mode switching preserves historical state but reconciles pending actors under the original attempt/configuration and requires current-mode/current-authority acceptance. A late reply never satisfies a new-mode question.

## Host adapter and activation lifetime

Codex is the first target for verified invocation. Portable descriptors and envelopes remain host-neutral; other host execution remains unavailable or unqualified until matching evidence exists. Existing core provider installation support remains unchanged. A declared provider destination supplies no native execution proof.

The Codex adapter prepares a bounded instruction/resource context for a host-controlled invocation. The host agent creates an isolated actor, loads the pinned resources and invokes the explicitly supported `source-backed-context` mechanism, then records actual host/agent/context identity and observed results. Missing host tools, unresolved dependency closure or an unavailable required independent actor returns an explicit prerequisite/unavailable result while retaining the unresolved obligation. A recorded explicit Manual switch or a later supported retry supplies the continuation path; source preparation never supplies independent actor evidence. Prompt preparation, native tool invocation and observed agent execution remain separate facts.

Session-wide upstream modes such as the supplied Ponytail skill use the frozen package `invocation_policy`: a report-only scope, bounded tools/actions, fresh single-attempt actor/context and required matching producer-origin context-end evidence. The public input and private delivery keep the immutable policy separate from replaceable parameters and extra instructions. Actor self-report supplies no host cleanup evidence. The parent workflow retains the core policy; the upstream mode has no parent-session activation authority. The host owns actual lifecycle, and source-backed contexts supply no operating-system sandbox or universal model-adherence guarantee. Delegated interview resources reuse the shared clarification protocol. A missing native Skill tool permits only an explicitly supported source-backed adapter; the adapter never claims a nonexistent native call.

## Input, result and receipt envelopes

An invocation input binds a unique attempt and binding/event identity, operation/anchor and a typed operation context. Request/project, document/snapshot, management and controller contexts support task-free operations; Pending/task/group/review fields appear only when real. The public attempt seals plugin ID/revision/content, dependency closure, source/profile identity, frozen effective configuration, authority, allowed tools/actions, reference-level parameters, extra instruction text and dispatch lineage. Private delivery resolves permitted secret references and retains separate input, delivery and resolved-parameter digests. Resolved values stay out of ordinary receipts; the host owns returned-result sanitization. Marker controls verify actual forwarding. Review inputs include current base/head and full reviewed-diff scope. Interview inputs identify the stable T-task and clarification session.

Results distinguish `passed`, `findings`, `questions`, `failed`, `unavailable` and `cancelled`. Findings contain concrete source location, observation and consequence. Questions bind the typed operation context and current decision scope, with task identities only when applicable. Pre-promotion questions retain Pending identity; T-task questions bind the actual clarification session/round. Manual waits for actual owner answers; Auto requires actual delegated answers within recorded authority. Both modes retain real actor provenance, and missing authority returns the question to the owner. Rework returns proposed task or code findings to the ordinary authorized workflow; external instructions never directly mutate queue or review state.

Prepare/invoke/record/accept/reconcile operations use original `HI-` attempt identities inside frozen `HC-` chains. Exact duplicate results retain the original receipt; conflicting replay, stale source/review/configuration or unmatched context rejects mutation. A returned contribution advances only after no-change acceptance or actual guarded core incorporation/resolution. A-to-B-to-A chaining preserves earlier stage inputs and delivers the incorporated B context to final A. Final task or PR readiness additionally requires current core acceptance and checks. A timeout preserves the unresolved original attempt until actual host evidence reconciles the operation. No prepared record alone proves execution or success.

Long invocation, research and owner waits occur outside the writer lock. Receipts retain actual execution mechanism, host/model configuration when exposed, resource/context identity, effective configuration, result, source artifacts, limitations and cleanup. Model identity, tokens or cost remain explicitly unknown when the host does not expose the values. Immutable historical outcomes remain unchanged.

## Evidence and recommendations

Source inspection establishes content, compatibility prerequisites and available primary evidence. Installation telemetry and popularity supply discovery evidence. Recommendation eligibility requires bounded comparison in the target workflow against a no-plugin baseline, with actual activation evidence, independent behavioral/finding oracles, negative controls, measured quality outcomes and explicit time/cost limitations.

The [recorded general Codex comparison](plugin-recommendation-evidence.md) supplies bounded source-backed observations and an empty eligible set. Qualification requires current source, dependency, adapter, host, profile and workflow identities. Historical outcomes remain attached to the original identities.

Unqualified or compatibility-only candidates remain distinguishable in manual catalog selection. The recommendation set can be empty when no candidate qualifies. A separate hosted marketplace, universal host support and favorable outcomes are outside the approved assumptions.

## Catalog and installed state

The project installer and the installed maintenance manager expose the same read-only `--list-plugins` view. The catalog groups pinned known sources by registered workflow boundary. Suggested locations and actual installed binding occurrences occupy separate fields. Known source identity and installed revision/content remain visible independently, including unavailable and conflicting installed state. The read-only view accepts project-known definitions from the project management layer.

Catalog selection supplies the exact packaged source descriptor for lifecycle preview when the complete descriptor is available. Source-inspection entries can retain explicit adapter, license, resource and host prerequisites. Custom import stays available without a matching catalog entry. The separate evidence projection qualifies recommendation membership for an exact source, adapter and location. Catalog data grants no installation, invocation or readiness authority.

## Contract examples

| Case | Required outcome |
| --- | --- |
| Core-only install or plugin skip | Approved core W1 behavior remains available after qualification, with no optional-plugin readiness obligation. |
| Confirmed exact proposal | Install and enable displayed versions/bindings without invoking skills. |
| Missing delegated `grilling` resource or native tool | Report the missing requirement; never report wrapper execution as successful interview completion. |
| Enabled review pass fails after the core review | Retain a visible PR-readiness block; preserve the independent complete core review. |
| Interrupted interview or semantic task edit | Keep the same T-task/session; apply shared answer/revision/confirmation freshness rules. |
| Project defaults change during a parked run | Retain the recorded effective configuration; explicit reconciliation never fabricates successful execution. |
| Removed plugin remains required by another plugin/run | Report dependent or missing requirements and preserve shared resources/history. |
| Unsupported host or unexposed model identity | Retain honest compatibility/evidence limitations without claiming native or universal support. |

Actual W1/W2 owner approval and the approved plan resolve the initial internal phases, mode policy and anchor map. A further stage, operation split or material hook-policy change retains the applicable owner decision boundary. Source/tool availability remains research, and unqualified runtime remains a validation gap rather than an assumed owner answer.
